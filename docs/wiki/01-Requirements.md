# 01 · Requirements (SRS v0.3)

EVE Distance Meter answers one question: **when a notification names a solar system, which of your characters is the
fewest stargate jumps away, what is it flying, and which way would it go?** You then log that character in yourself.

Requirements use EARS phrasing. Priority: **M** Must, **S** Should, **C** Could. *Status* and *Verified by* trace each
requirement to the code and to the automated tests in this repository (0.3.0, extended up to 0.8.0, plus the members-only tabs, Thera / Turnur, the structure scout rework, ESI error-limit handling and Python 3.13 / published-image deployment that follow it, marked "after 0.8.0").

## Decisions

| ID | Decision |
| --- | --- |
| D1 | The existing bot is not modified or integrated. The user reads its Discord channel and gives the app the target system by typing it or pasting the message text. |
| D2 | One shared Python core with two front ends: a Web UI in Docker (built, 0.3.0) and a Desktop UI in PySide6 (planned, M3). |
| D3 | Every token comes from the user's own registered EVE application (client_id + secret known). |
| D4 | Routes are computed in the app: breadth-first search over the SDE stargate graph returns jump count and the full route. |
| D5 | Each instance keeps its own encrypted local store; characters move between instances with a JSON bundle. |
| D6 | Both UIs use the same SSO flow (authorization code + client secret), so bundles are interchangeable. |
| D7 | The star map is a 2D top-down projection of SDE coordinates, drawn by the app (canvas). No external map or route site. |
| D8 | The app writes to the game client only when the user asks: **Set destination** sets the autopilot destination of an online character (`esi-ui.write_waypoint.v1`, revised in 0.7.0; until then the app never wrote to the client). Nothing else is sent, and nothing is sent on its own. |
| D9 | Structure attack timers are not public (only the owner corporation's directors get them). Structure alerts use public killmails from zKillboard's live feed instead: destroyed, combat on grid, structure firing (0.7.0). |
| D10 | A static roster entry is never sent to ESI: it has no tokens, no ship, no online state and never enters the refresh or rate-limit paths. Its only data are a name, a system and the moment it was uploaded (0.8.0). |
| D11 | One roster pool per main, merged on upload and keyed by the normalised character name: an upload adds new names and moves names already there. No named sets, no versions. |
| D12 | A roster entry whose system does not resolve is stored unresolved with its reason and up to three suggestions, not rejected; only the file as a whole can be rejected. |
| D13 | Roster characters are ranked on their own tab of the ranking view and listed on the Roster page; they never mix into the live list and never take the place of a live character, on the Alerts page included. |
| D14 | ESI notifications are used after all (this revises the 0.5.0 decision): asset-safety and structure notices reach the character itself, so no corporation role is needed. `esi-characters.read_notifications.v1` joins the **required** scopes; a character that does not grant it is Limited and is not polled. |
| D15 | ESI caches notifications 600 s per character, so the poller asks only for the characters whose cached copy has expired, each at ESI's own `Expires` time (not a fixed 600 s after the last read, which let notifications arrive up to ~15-20 minutes late); transient errors are retried after 60 s (the ESI client revalidates with ETag). A new notification is on the page within about a minute of ESI publishing it. |
| D16 | The **Notifications** and **Structures** tabs belong to one alliance (BB, ID 99010320): both are shown only to a main whose alliance is in `access.alliance_ids`. The alliance is read from ESI `/characters/{id}` at sign-in, stored on the account and re-read every `affiliation_hours`. For every other character the links are hidden and the pages and APIs answer 404 (after 0.8.0; before it only Notifications was gated, by `notifications.alliance_ids`). |
| D17 | The Notifications page is **site-wide**: it lists the notifications of every registered character that has a valid refresh token (granted the notifications scope, not Re-auth required), whoever linked it and whatever its ranking enabled switch says. Any member sees all of them, not only those of its own characters; the closest-character lists stay personal (after 0.8.0). |
| D18 | The Structures page lists every structure in which **any** registered character with a valid token holds an asset: ESI assets give the structure IDs (read page by page, only locations of type `other`), then ESI `/universe/structures/{id}` gives name, owner, type and system. Every structure found is **saved in the database at once and kept until it is destroyed or unanchored** (404); access to it is not needed to keep the row. The list is pooled for all members; which character revealed a structure is never shown. |
| D20 | A character is polled for notifications only when its *Notifications* tick (default on) is set **and** it holds assets in at least `notifications.min_structures` (10) player structures (location id >= 1e12; NPC stations do not count), to spare ESI calls. |
| D22 | Notifications are pushed, not polled, on the last hop: the page keeps one request open (long poll) and reloads when the poller stores something; and they go to Discord through the wars webhook, one message per event that is edited as more characters receive it. ESI's 600 s cache per character remains the floor; reads are spread over that window so the earliest recipient decides. |
| D21 | Ansiblex gates: ESI has no gate list or access list, so each character's usable gates are those its own structure search (`esi-search.search_structures.v1`, term " » ") returns, read with `/universe/structures/{id}`; visibility is treated as usability and every gate costs one jump. |
| D19 | The Ranking choice **Gates only / Thera / Turnur** (one radio button per hub) uses EVE-Scout's public signature list. For a character and a target the route through the chosen hub is: gates to the listed system **closest to the character**, the wormhole into the hub, the wormhole out to the listed system **closest to the target**, gates on to the target; among equally close listed systems the one with the **higher security** wins. The wormhole counts as two jumps. Each button uses only its own hub as the mid-system. The hub route replaces the gate route only when it is **strictly shorter**; when entry and exit are the same system the plain gate route is shorter and the hub is skipped. Connections marked *End Of Life* are kept; J-space exits are skipped (no gates). The list is cached for 15 minutes. The map shows two gate legs joined by a wormhole leg. Roster ranking is not changed. |
| D23 | **Resolve unknown** is a background job (one at a time) that reads the structures without name, owner or system from `/universe/structures/{id}` (`esi-universe.read_structures.v1`) with the **characters that hold assets there** (`structure_sightings`): those linked to the signed-in main first, then other sighters, and the main itself last. Order of work: structures on ESI's public list (`/universe/structures/`, any token will do), then structures with a sighter that was never refused, then the rest by `checked_at`. A 403 is stored per pair in `structure_refusals(structure_id, character_id, refused_at)`; a pair refused less than `structures.no_access_refresh_hours` (336) ago is not asked again, by the button or by the hourly scout, and a structure with nobody left to ask is not sent to ESI at all (counted *skipped*). 200 stores the details, 404 marks it gone, both delete the refusals of that structure. ESI's error window is waited out (the job sleeps until it resets, never sends while it is low) instead of ending the run, so one click works through the whole list. ESI cannot search a structure by ID (character search needs a name fragment and returns only structures the character may dock at), so there is no search step; `/corporations/{id}/structures/` is not used because it needs a new scope and the Station_Manager role (after 0.8.0). |
| D24 | Structures nobody here may read are matched against two public datasets, **EVE Ref** (`structures-latest.v2.json`, ESI's own fields by structure ID) and **Adam4EVE** (CSV). EVE Ref outranks Adam4EVE; neither replaces live ESI data, and a match is shown as "Historical details" with its source. Each dataset is fetched at most once a day (a failure after an hour), capped by size (`everef_max_mb`), and EVE Ref can be switched off (`everef_enabled`) (after 0.8.0). |
| D25 | **Dockable structures**: the scout also finds structures a character may dock at without assets there, through ESI's character search (`GET /characters/{id}/search/?categories=structure`, scope `esi-search.search_structures.v1`), which returns only structures that character may dock at. Live ESI **matches the start of a name (or of a word), needs 3+ characters and finds nothing for punctuation-only terms**: " - " and " » " return 0, "Odette" and "Ode" return structures, "dette" does not. A substring search of the " - " in every Upwell name ("<System> - <Name>") therefore does not work; instead each character is searched with the **prefixes of all solar system names** (`dock_search_prefix_len`, 3: about 4 100 distinct case-insensitive prefixes in the shipped universe, each remembering its systems), in the order: last known region, regions where it sights or may dock, rest of k-space by region, J-space. `dock_search_max_terms` (200) terms per character and due run, a persisted cursor, the end of the list completes a **pass** (`passes`, `pass_started_at`). The first pass goes on at every scout run, afterwards a character is due every `dock_search_hours` (24). A term that answers `dock_search_cap` (500) structures or more is split into the full system names behind the prefix (they count against the budget); a full name still at the cap keeps what came back and counts as *capped*. A term that answers below the cap is complete: rows recorded under it (`structure_access.term`) that it no longer returns are dropped; rows nobody refreshed for `max(30 days, 2 x the expected pass)` age out. `dock_search_punctuated: full` searches systems whose prefix has punctuation (H-PA29) by full name. **Not verified against live ESI**: whether such punctuated prefixes match and the real cap; `evedm structures search-probe --self-test` checks the first on known structures and recommends the setting. Who may dock is **pooled as counts only**: the shared list shows `dock_by` (a number), never which character, like `seen_by`; the stored pair is used only to choose a token that may read the structure, first before sighters (D23). The Ansiblex search (" » ") returned 0 for the same live character; Ansiblex is unchanged and the self-test reports its live count next to the stored gates (after 0.8.0). |
